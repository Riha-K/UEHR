01

Project Elevator Pitch

Have a 60–75 second answer ready. Then dive into modules if they ask.

“UEHR is a multilingual EHR form generator. Instead of hard-coding clinical forms, we generate them dynamically from openEHR archetypes. An archetype is serialized to JSON, and the React frontend reads that JSON to build the GUI — mapping datatypes like quantity, text, and coded text to input components. The form supports language neutrality using translations already present in the archetype (ISO 639-1 codes like en/ja). On submit, we call the local Snowstorm API to bind medical terms to SNOMED CT concept IDs for semantic interoperability, then persist the JSON payload in MongoDB through a Node/Express backend. So the system addresses syntactic interoperability via openEHR, semantic interoperability via SNOMED CT, and usability via dynamic multilingual forms.”

Problem & Objectives

From the project report abstract — these four objectives are your interview backbone.

Why static forms fail

Clinical needs change. If forms are hard-coded, adding a field means redesigning the whole UI and redeploying. Doctors/domain experts should drive structure via archetypes — not wait on developers for every field change.

Four objectives

  • Generate medical forms dynamically from archetypes/templates
  • Provide language neutrality in the generated form
  • Persist form data in a suitable database
  • Terminology binding using SNOMED CT

Motivation (India / usability)

Language barriers in healthcare UIs reduce adoption. Multilingual forms improve usability in diverse populations. Standardization (openEHR + SNOMED) enables exchange without ambiguity.

Novelty (report)

Combination of (1) multilingual dynamic forms from archetypes, (2) SNOMED CT semantic binding, (3) MongoDB flexible persistence — not just one of these alone.

03

Must-Know Concepts

If you only memorize definitions, memorize these. Interviewers will probe them.

EHR

Electronic Health Record — digital patient medical information accessible to clinicians/systems.

openEHR

Open standard for EHR structure/content. Separates reference model (software) from clinical knowledge (archetypes/templates managed by clinicians).

Archetype

Reusable clinical model for a concept (e.g. Blood Pressure) with fields, constraints, datatypes, translations. Written in ADL, can be compiled to AOM and serialized to JSON.

Syntactic interoperability

Systems can exchange structured data using a shared format/model (here: openEHR archetypes / standardized structure).

Semantic interoperability

Systems share meaning of terms. “Systolic BP” means the same concept everywhere — achieved via SNOMED CT IDs, not just translated labels.

SNOMED CT

Huge multilingual clinical terminology. Concepts have IDs. Bound via local Snowstorm server API (/snomed/MAIN/concepts?term=...).

Interview one-liner: “openEHR gives us the structure (syntax); SNOMED CT gives us shared meaning (semantics); React+MongoDB give us usable multilingual capture and storage.”

STEP 01
Obtain / design archetype

Clinical concept (e.g. Blood Pressure) is modeled as an openEHR archetype/template (Archetype Designer / CKM). Contains attributes, constraints, datatypes, and translations.

↓
STEP 02
Compile + serialize to JSON

ADL → Archetype Object Model (via AWB) → JSON. JSON holds tree structure, inputs, localizedNames, optional termBindings, languages list.

↓
STEP 03
Dynamic GUI generation (React)

Frontend fetches /{rmType}/{archetypeId}.json, walks archetype.tree.children, and renders InputComp widgets based on datatype (DECIMAL / TEXT / CODED TEXT → number, text, dropdown).

↓
STEP 04
Language neutrality

User picks language from dropdown (LangSelector). Labels are taken from archetype translations / localized names for that ISO code (en, ja, it, …). Form regenerates labels without new hard-coded UI.

↓
STEP 05
User fills + submits

Patient fields + clinical fields collected. On submit, frontend recursively builds a filtered JSON of values (and empty branches pruned).

↓
STEP 06
Terminology binding (SNOMED CT)

For nodes without existing SNOMED bindings, call Snowstorm: GET /snomed/MAIN/concepts?term=.... Attach termBindings["SNOMED-CT"] = conceptId so meaning is language-independent.

↓
STEP 07
Persist in MongoDB

POST http://localhost:5001/ → Express insertOne(req.body) into MongoDB. Flexible document schema fits evolving archetypes (Observation, Composition, etc.).

05

Four Modules (Deep Dive)

A. Dynamic GUI Generation

Figure 3.2 — GUI generation module (report)

What it does

Converts archetype JSON into a usable medical form. Traverses data attributes and creates inputs according to constraints.

Datatype → widget mapping

  • DECIMAL / Quantity → numeric input
  • TEXT → text input
  • CODED TEXT → dropdown of valid codes
Q: Why generate forms from archetypes instead of hard-coding?
Archetypes change with clinical knowledge. Dynamic generation means a new/updated archetype JSON can produce a new form without rewriting React screens for every field.

B. Language Neutrality

Figure 3.7 — Language neutrality module (report)
Q: How does multilingual support work?
Archetypes include translations (e.g. English + Japanese for “blood pressure”). JSON keeps them under localized names keyed by ISO 639-1 codes (en, ja). The React LangSelector switches ln state; InputComp displays the label for the selected language.
Q: Is translating the UI enough for interoperability?
No. Labels help humans (usability). Machines need stable concept IDs — that’s why we also do SNOMED CT binding after submit.

C. Data Persistence (MongoDB)

Figure 3.8 — Data persistence module (report)
Why MongoDBExplanation
Native JSON/BSONForm payload is already a document tree
Flexible schemaArchetypes evolve; different RM types (Observation, etc.) differ in shape
ScalabilityHandles growing volumes of health-record documents
Simple backendExpress insertOne is enough for MVP persistence
Q: Why not PostgreSQL / SQL?
Possible, but you’d need frequent schema migrations as archetypes change, or heavy EAV/JSON columns anyway. MongoDB’s document model matches variable clinical form trees with less friction for this use case.

D. Terminology Binding (SNOMED CT / Snowstorm)

Figure 3.11 — Terminology binding implementation (report)
// From Form.jsx — Snowstorm lookup GET http://localhost/snomed/MAIN/concepts?term=fever&offset=0&limit=1 → response.items[0].conceptId → termBindings["SNOMED-CT"] = conceptId
Q: What problem does terminology binding solve?
The same clinical idea can be written in many languages/spellings. Storing a SNOMED conceptId makes the record semantically comparable across systems and languages.
Q: Why Snowstorm and not only FHIR Terminology API?
Snowstorm is SNOMED’s terminology server; the project uses openEHR + local Snowstorm endpoints. FHIR API is an alternative; report chose Snowstorm for local hosting and concept search suited to our binding step.

Code-Level Talking Points

Be ready for “show me what the code does” — based on Form.jsx and backend/api.js.

Form.jsx

  • Loads archetype JSON by route params rmType, archetypeId
  • Adds patient_id / patient_name fields
  • LangSelector sets ln
  • Recursive filterUtil builds submission tree
  • getSnomedData / getTermBindings attach concept IDs
  • axios.post('http://localhost:5001/', data)

backend/api.js

  • Express app, CORS enabled
  • POST / → insertOne(req.body)
  • Port 5001
  • Minimal API focused on persistence
Honest interview note: Backend is intentionally thin (insert). Most intelligence is in the frontend form pipeline + Snowstorm integration. If asked how you’d productionize: auth, validation, audit logs, FHIR export, retry/queue for terminology calls, server-side binding.
09

Interview Q&A Bank

Q: Explain UEHR in one minute.
Use the elevator pitch. End with the three pillars: dynamic forms, multilingual usability, SNOMED + MongoDB interoperability/persistence.
Q: What is an archetype? Give an example.
A reusable clinical information model. Example: Blood Pressure archetype with systolic, diastolic, mean arterial pressure, interpretations, protocol/state sections — plus translations and constraints.
Q: Syntactic vs semantic interoperability?
Syntactic: shared structure/format so systems can exchange data (openEHR). Semantic: shared meaning of concepts (SNOMED CT IDs), so “fever” in any language maps to the same concept.
Q: How is the form generated dynamically?
Archetype JSON is fetched; React recursively renders children with InputComp; widget type comes from archetype datatype/constraints — not a fixed HTML form per disease.
Q: How do you support Japanese / Italian forms?
Translations already exist in the archetype/JSON localized names. User selects language code; UI reads that language’s labels. No separate hard-coded Japanese React page.
Q: What happens on Submit?
Build filtered JSON of entered values → resolve SNOMED IDs via Snowstorm for terms → POST to Express → insertOne into MongoDB → success alert / navigate home.
Q: Why MongoDB over MySQL?
Clinical form trees vary by archetype and evolve over time. Document DB avoids constant relational migrations and stores JSON naturally.
Q: What is Snowstorm?
A SNOMED CT terminology server (with Elasticsearch) exposing REST APIs to search concepts and fetch concept IDs — used for terminology binding.
Q: openEHR vs HL7 FHIR?
Both are major health-interop approaches. openEHR emphasizes archetypes/dual-model clinical content; FHIR emphasizes resource-based APIs for exchange. This project is openEHR-centered with SNOMED for semantics; FHIR could complement for API exchange.
Q: What challenges did you face?
Mapping diverse archetype datatypes to UI widgets; ensuring translations render correctly; integrating local Snowstorm (Elasticsearch + Nginx CORS); designing persistence that survives archetype changes.
Q: How did you evaluate success?
Generated forms for multiple archetypes (blood pressure, health risk, etc.); verified language switching; verified MongoDB documents contain submitted values and SNOMED termBindings.
Q: What was YOUR contribution / what can you claim?
Be honest about team context if asked. On your resume you list UEHR with React/Node, openEHR dynamic forms, SNOMED via Snowstorm, MongoDB. Defend architecture, interoperability concepts, and code paths you understand end-to-end.
Q: How does this relate to an AI / document role (e.g. ARC)?
UEHR turns structured clinical knowledge models into usable digital capture with standard codes — similar spirit to digitizing documents into AI-ready, interoperable assets. Experience with APIs, JSON pipelines, and semantic coding transfers to document intelligence systems.
Q: Security / privacy concerns?
Health data is sensitive (PHI). Production needs authN/Z, encryption, audit logs, consent, and compliance (e.g. HIPAA-like controls). Current project is an academic usability/interop prototype, not a production hospital system.

Quick-Hit Definitions

Q: What is ADL?
Archetype Definition Language — textual language for defining openEHR archetypes.
Q: What is AOM?
Archetype Object Model — object representation after compiling ADL; can be serialized to JSON.
Q: What is CKM?
Clinical Knowledge Manager — online repository of archetypes/templates/term sets.
Q: What is ISO 639-1?
Two-letter language codes (en, ja, it) used to tag archetype translations and the language dropdown.
Q: What is RM type?
Reference Model type in openEHR (e.g. OBSERVATION) — used in routing/loading the correct archetype JSON.
Q: Usability in this project means?
Clinicians/patients can use forms in their language; forms adapt from archetypes without constant developer redesign.
